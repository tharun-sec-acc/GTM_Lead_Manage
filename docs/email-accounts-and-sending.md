# Email accounts, sending and conversations

The platform has two sending paths:

1. **OAuth mailbox sending** (`backend/app/email_provider.py`, `backend/app/email_sender.py`,
   `backend/app/email_accounts_api.py`) for Gmail/Google Workspace and Microsoft 365/Outlook accounts, one
   connection per user/organization, with inbox synchronization.
2. **Legacy app-password SMTP/IMAP** (`backend/app/mailer.py`, `backend/app/mailbox.py`) used by campaign
   follow-ups with `GMAIL_ADDRESS` and `GMAIL_APP_PASSWORD`.

Both remain in the codebase; campaign dispatch still uses the legacy SMTP path and its safety gates.

## 1. OAuth connections

`POST /api/email-accounts/oauth/google/start` and `/oauth/microsoft/start` begin an authorization-code flow with
a signed, cookie-bound `state`; the callbacks (`/oauth/google/callback`, `/oauth/microsoft/callback`) exchange
the code and store an `oauth_connections` row scoped to the active organization and user. Refresh and access
tokens are Fernet-encrypted, scopes are recorded, and status is one of `connected`, `expired`,
`reauth_required`, `error` or `disconnected`.

The email flow requests `openid`, `userinfo.email`, `gmail.send` and `gmail.readonly` for Google, and
`offline_access`, `User.Read`, `Mail.Send` and `Mail.Read` for Microsoft. Calendar, Meet, Drive and Teams scopes
come from the separate organizer connections used by the meetings and booking modules, not from this email flow.
A tenant may require administrator consent; without it the callback returns an error instead of a broken
connection.

| Method and path | Purpose |
| --- | --- |
| `GET /api/email-accounts` | List connected accounts for the organization with status, scopes, default flag and last sync |
| `POST /api/email-accounts/{id}/default` | Mark the user's default sender |
| `POST /api/email-accounts/{id}/disconnect` | Clear the local encrypted credentials (provider consent is not revoked) |
| `POST /api/email-accounts/{id}/sync` | Pull recent inbox mail through the provider API and ingest replies |
| `POST /api/email-accounts/send` | Send a single HTML email (optional text part, CC/BCC, lead/contact association) and record it |

Provider behavior:

- `GmailAPIProvider` refreshes the token, sends MIME through the Gmail API and syncs inbox messages.
- `MicrosoftGraphProvider` refreshes the token through the Microsoft identity platform, sends through Graph
  `sendMail` and syncs the mailbox.
- Incoming mail is passed to `reply_sync.ingest_incoming_email`, which matches the sender to an enrollment and
  records a reply so follow-ups stop for that recipient.

Sending only proceeds when the provider credentials are valid and the account is `connected`. Mailbox-level
rules, suppressions and reply stops still apply to campaign sending; direct account sending is an explicit
sales action.

## 2. Outreach surfaces

| UI / endpoint | Behavior |
| --- | --- |
| `/followups` campaigns, `outreach-workspace.tsx` | Draft, approve and schedule follow-up sequences per recipient |
| Bulk outreach modal (`bulk-outreach-modal.tsx`), `GET /outreach/recipients`, `POST /outreach/bulk-send` | Select saved contacts or paste addresses, review, and send an approved message through a connected account |
| Direct outreach panel (`direct-outreach-panel.tsx`), `POST /leads/{lead_id}/direct-outreach` | Compose and send one message for a lead without creating a campaign |
| Lead conversation workspace (`lead-conversation-workspace.tsx`), `GET /conversations`, `/{id}/reply`, `/{id}/followup-status`, `/{id}/generate-draft` | Unified reply inbox with follow-up status and reply sending |
| `/api/email-accounts/send` | Account-level send used by the composer |
| `POST /attachments/upload`, `GET/POST /messages/{id}/attachments` | Attachment upload and per-message attachments, also usable in bulk outreach |

Drafts generated by Bedrock are never auto-approved. Recipient selection, subject and body are still reviewed by
the salesperson, and every message keeps the existing approval/suppression gates.

## 3. Campaign sending safety (legacy SMTP path)

`MAIL_SEND_ENABLED` is `false` by default. When enabled, a due message is sent only if the campaign is active,
the recipient is not stopped or suppressed, the exact draft is approved, the mailbox sync completed without
unresolved delivery reports, Gmail SMTP credentials work, and the rolling 24-hour budget
(`DAILY_SEND_LIMIT`) allows another attempt. `MAIL_UNSUBSCRIBE_ENABLED=true` additionally requires
`PUBLIC_BASE_URL` and appends unsubscribe headers/footer. Optional tracking (`TRACKING_ENABLED`) requires the same
public HTTPS base.

SMTP acceptance is recorded as `smtp_accepted`; it is **not** proof of delivery. A message left `sending` or
`unknown` must be reconciled through the UI before retrying. See
[email capacity and rate limits](email-capacity-and-rate-limits.md) and
[multi-recipient outreach](multi-recipient-outreach.md).

## 4. Configuration

| Variable | Purpose |
| --- | --- |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` | Google OAuth app used for Gmail sending and Google Calendar/Meet |
| `MICROSOFT_TENANT_ID`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_REDIRECT_URI` | Microsoft Entra app for Outlook sending, calendar and Teams |
| `GOOGLE_TOKEN_ENCRYPTION_KEY` / `MICROSOFT_TOKEN_ENCRYPTION_KEY` | Fernet keys for the encrypted refresh tokens (OAuth connection rows use the same keys) |
| `PUBLIC_BASE_URL` | Links in invitation, unsubscribe and tracking mail |
| `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD` | Legacy SMTP/IMAP account used by campaign sending |
| `MAIL_SEND_ENABLED`, `MAIL_UNSUBSCRIBE_ENABLED`, `TRACKING_ENABLED`, `DAILY_SEND_LIMIT` | Send gates and budget |

## 5. Limitations

- Automated coverage: `backend/tests/test_email_accounts_and_sending.py` and the follow-up/generation suites;
  provider calls are mocked, so no live Gmail or Graph send has been verified here.
- There is no per-provider quota query; the daily limit is an application counter.
- The account sync is a recent-message pull, not a full delta/history sync, and reply matching is best effort.
- Attachments and uploaded files use the local `attachments_data` volume through `app/storage.py`
  (`ATTACHMENT_STORAGE_DIR`, default `/app/attachments`, with a temporary-directory fallback). Only meeting
  artifacts have an optional S3 path; message attachments have no object-store backend.
- The email OAuth redirect URIs are hard-coded to `http://localhost:8000/api/email-accounts/oauth/google/callback`
  and `/oauth/microsoft/callback`, and the post-connect redirect goes to `http://localhost:3000/settings/email-accounts`.
  Register those exact callbacks, and change the constants for any non-local deployment.
- Bounce and DSN handling remains best effort and needs an unresolved-delivery review before sending continues.
